## 1. 为什么写完不等于做完

LLM 生成代码时，**语法错误很少见，语义错误很常见**——而且语法正确会让它更有欺骗性。

一个从不检查就交付的 skill，最可能的问题：

- 脚本能跑但算错（符号反了、基准错了）
- 文档写的参数代码里不存在
- 引用了不存在的文件
- 留了测试产物

这些都不影响"看起来完成"，但会毁掉用户对整个 skill 的信任。

## 2. 可执行件：合成数据自检

### 原则

> **构造一个你知道正确答案的数据集，然后验证脚本能否复现它。**

### 四步

```
1. 设计 DGP：你知道真相的数据生成过程
2. 跑脚本
3. 逐个关键数字手工核对
4. 检查单调性与符号合理性
```

### DGP 设计示例

```
已知真相：
  - 真实信号 f，模型 A 捕捉 70%，模型 B 是纯噪声
  - 组合应呈现单调的收益梯度
  - 成本后净值应低于毛收益，且随成本上升而下降
```

预期输出：
- 模型 A 样本外 R² > 0、方向准确率 > 50%，模型 B ≈ 0
- 嵌套检验（CW、DM）判定 A 优于 B
- 分组收益单调
- **净收益 < 毛收益，且成本越高净值越低**

### 手工核对清单

| 检查 | 怎么验 |
|---|---|
| 毛值 − 成本 = 净值 | 直接减，看是否对得上 |
| 成本 ∝ 换手 × 单边成本 | 换手翻倍，成本是否翻倍 |
| 盈亏平衡成本 | 在该成本下净收益是否恰为 0 |
| t 值量级 | 是否与样本量、离散度相称 |
| 单调性 | 成本↑时净值应↓；信号↑时收益应↑ |
| 空头符号 | 多空成本是否扣了两次 |

## 3. 典型 bug 清单

以下都是实测抓到的真实缺陷，值得逐条对照检查。

| 症状 | 根因 | 检查方法 |
|---|---|---|
| 成本类输出恒等于毛值 | 权重/换手变量定义错导致成本恒为 0 | 单独打印换手率，确认非零 |
| **成本越高净值越高** | 空头腿成本被加回来了（`净顶 − 净底` 应为 `净顶 + (−净底) − 成本底`） | 检查符号，验证单调性 |
| 统计量不随样本变化 | 变量在循环外被覆盖/累加 | 检查作用域 |
| 顺序类结果异常 | 处理组赋值顺序（先算后记） | 检查 update 时机 |
| 控制台中文/特殊字符崩溃 | Windows GBK 编码 | `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` |
| Windows 下删除命令被拦截 | 硬删除策略 | 走可恢复删除（`rm -- <path>` 单条顶层命令） |
| 换行符被改 | 编辑时未保持 CRLF/LF | 检查 diff |

**"成本越高净值越高"这一条尤其值得记住**：它不会报错，只会让结论悄悄反号。

## 4. 文档-代码同步

逐条核对，双向：

**文档 → 代码**
- [ ] 每个命令都能跑
- [ ] 每个参数在 argparse 中真实存在
- [ ] 每个默认值与代码一致
- [ ] 每个提到的输出文件真实生成
- [ ] 每个引用的路径真实存在

**代码 → 文档**
- [ ] 每个必填参数在文档中有说明
- [ ] 每个重要输出在文档中有解释
- [ ] 没有未说明的隐含行为

**最快的方法**：照着文档里的示例命令，原样跑一遍。

## 5. 归属与诚实声明

`ATTRIBUTION.md` 至少包含：

```markdown
## 来源
| 来源 | URL | 用途 | 分级 | 是否抓到 |
（**没抓到的也要写，并说明原因**）

## 可靠性分级
哪些结论来自哪一级来源

## 版权声明
未复制原文；标题属事实性引用；摘要是独立概括

## 准确性边界
哪些是原文陈述，哪些是推断；框架的适用边界
```

**为什么要写"没抓到的"**：这是可信度的来源。隐瞒缺失会让用户误以为信息完整。

## 6. 清理

交付前移除：

- [ ] 测试生成的数据/输出目录
- [ ] `__pycache__`、`.pyc`
- [ ] 临时日志
- [ ] 草稿文件、被注释掉的大段代码

**注意**：清理要用**可恢复删除**（单条顶层 `rm -- <path>`），不要用硬删除命令，也不要把删除写成脚本绕过。
