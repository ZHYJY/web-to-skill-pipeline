## 1. 为什么必须建取证链

抓取失败在真实场景里是**常态**。学术主页最常见的组合恰好是最容易失败的组合：

| 想抓 | 通常的命运 |
|---|---|
| Google Scholar 主页 | 人机验证，几乎必拦 |
| 出版社付费墙论文 | 只能拿到摘要 |
| 期刊官网 | 大量 JS 渲染 |
| ORCID | 常需 JS |
| 个人学术站（Google Sites） | HTML 巨大，正文被截断 |
| 机构教师页 | **最容易成功** |

**关键认知**：当主源被拦时，**通常有更好的替代源，而不是"拿不到"**。机构教师页往往包含比 Scholar 更多的信息（完整摘要、获奖、研究方向标签）。

**致命错误**：第一个 URL 失败后，用推测或训练记忆填补。这会产出看起来很像样、实则无法核实的 skill。

## 2. 降级顺序

按信息密度排序。高密度源优先。

### 1️⃣ 原始 URL
先试用户给的。

### 2️⃣ 同主体其他站点
学术场景的高价值替代：

| 来源 | 通常含有什么 | 注意 |
|---|---|---|
| 机构教师页 | 完整摘要、获奖、研究方向标签、期刊列表 | **学术场景首选**，往往信息最全 |
| 个人学术站 | 论文全清单 + 状态（已发表/工作论文） | Google Sites 体积巨大，正文会被截断，需分段取 |
| 实验室/课题组页 | 研究方向、成员、数据资源 | 常有合作项目信息 |
| 个人 CV（PDF/Google Drive） | 完整发表清单、分工说明 | 常链在页面上 |

### 3️⃣ 结构化档案

| 来源 | 可取 | 局限 |
|---|---|---|
| ORCID | 完整发表列表 | 缺摘要 |
| arXiv | 全文（预印本） | 只覆盖部分学科（SSRN 覆盖经济金融） |
| SSRN | 经济金融预印本全文 | 分卷下载常需登录 |
| Semantic Scholar API | 结构化元数据、引用数 | 有速率限制 |
| RePEc / IDEAS | 经济学论文索引 | 摘要常缺 |
| DBLP | 计算机领域完整 | 金融覆盖弱 |

### 4️⃣ 会议/期刊页
拿摘要、版本信息、获奖记录。

### 5️⃣ 二手汇总
综述文章、同行总结、机构新闻稿。
**必须标注为二手来源**，且不得用于推断方法细节。

### 6️⃣ 明确告知抓不到
把可得清单交给用户，问是否有补充材料。

## 3. 拦截类型识别

| 类型 | 页面特征 | 判定 | 处理 |
|---|---|---|---|
| **CAPTCHA** | `recaptcha`、`g-recaptcha`、`captcha-form`、`unusual traffic`、`captcha` | A 级陷阱 | **换路径**，不尝试绕过 |
| **403 Forbidden** | HTTP 状态 | | 换路径、降低频率 |
| **429 Too Many** | HTTP 状态 | | 等待后退避重试或换路径 |
| **JS 空壳** | 可见文本 < 500 字符但 HTML > 50KB | | 找静态镜像或换路径 |
| **付费墙** | `purchase`、`subscribe`、`institutional access`、`rent this article` | | 只取可见摘要 |
| **登录墙** | `sign in`、`log in`、`password` | | 换路径 |
| **软 404** | 200 但内容是"页面不存在" | | 换路径 |

📄 `scripts/fetch_probe.py` 可批量探测并自动分类。

### ⚠ 两条实测得出的重要规则

**规则一：拦截是"客户端/路径相关"的，不是绝对的。**

实测记录：同一个 Google Scholar 个人主页 URL，
经运行时抓取工具请求时返回**人机验证页**；
改用标准 HTTP 客户端请求时返回**正常页面**（含页面结构与目标内容，无验证码特征）。

推论：

- **单次失败 ≠ 永久不可用。** 判定不可用前，至少换一次标准客户端重试。
- 换客户端是**正常的网络行为**，不是绕过；绕过验证码才是硬边界。
- 但不要把重试当万能：若两次都失败，就按降级顺序换路径，不要反复轰炸同一站点。

**规则二：传输成功 ≠ 内容可用。**

上面那次成功的 Scholar 请求，HTTP 200、可见文本 5,960 字符，
但**论文标题并不在 raw HTML 里**——列表由 JS 渲染。

推论：

- `ok` 只说明"能拿到响应"，不说明"拿到了你要的内容"。
- 对已知 JS 渲染站点（Scholar / LinkedIn / X 等），即使判定 ok，
  也**必须人工确认目标内容确实在响应里**。脚本已对这类站点加 `content_note` 提醒。
- 正确做法：改用结构化 API（Semantic Scholar、ORCID、arXiv API）取数据，而非解析页面。

### 截断问题

抓取工具常有 token 上限。大页面（尤其 Google Sites、个人主页）会被截断，**中间部分丢失**。

应对：
- 优先抓**含目标信息的锚点页**（如 `.../papers` 而非首页）
- 抓取后**检查是否截断**（响应里出现 `truncated` 提示）
- 截断时换更精确的 URL 或分多次抓取不同 section
- **不要**把截断后的残缺内容当作完整来源登记

## 4. 按主体类型的取证地图

### 学术研究者
```
机构教师页 ──┬─→ 摘要 + 获奖 + 期刊列表
个人学术站 ──┴─→ 论文全清单 + 发表状态
ORCID/arXiv/SSRN ──→ 全文（补充方法细节）
```

### 框架/库（如某 JS 库的做法）
```
官方文档站 ──→ 用法与 API
源码仓库 ────→ 实现决策
Issues/PR ───→ 设计权衡与失败模式（极有价值）
```

### 工具/产品
```
官网 ──→ 定位与卖点
文档 ──→ 能力边界
更新日志 ──→ 演进决策（为什么改）
定价页 ──→ 商业模式约束
```

### 公司/团队实践
```
博客 ──→ 方法论陈述
工程/招聘页 ──→ 技术栈与优先级
开源项目 ──→ 实际做法
```

## 5. 交叉印证

**同一事实尽量来自两个独立来源。**

| 事实 | 来源 A | 来源 B |
|---|---|---|
| 论文清单 | 机构页 | 个人站 / ORCID |
| 期刊归属 | 机构页 | 期刊官网 / DOI |
| 方法细节 | 摘要 | 全文（SSRN/arXiv） |
| 获奖 | 机构新闻 | 期刊/会议公告 |

**冲突时**：两个来源都记下来，注明冲突，不要静默选一个。冲突本身常常是有信息量的（例如论文状态标注不一致，说明可能已发表但作者页未更新）。

## 6. 明确不做的事

这些是硬边界，不是能力限制：

- ❌ **不绕过 CAPTCHA 或付费墙**
- ❌ **不伪造抓取结果**，不把"我记得这个网站大概是…"写成抓取到的
- ❌ **不把训练记忆当作来源**。如果你没抓到某个事实，就标注"未核实"
- ❌ **不静默降级**：用户给了 Scholar URL 却只抓了机构页，必须明说

## 7. 交付给用户的话术

### 抓取部分成功

> 机构主页抓取成功，拿到完整履历、期刊列表和 5 篇论文的完整摘要。
> **Google Scholar 返回人机验证，未能读取。** 我用他的个人学术站补齐了论文标题与发表状态。
> 案例册里对每篇论文做了可靠性分级——有摘要的才推断方法设计，仅有标题的只做选题结构推断。

### 全部失败

> 这几个链接都被拦了（<原因>）。我没有绕过验证。可以用这些替代路径：<清单>。
> 你能提供本地保存的 PDF 或截图吗？

### 冲突

> 两个来源对 <事实> 的说法不一致：机构页写 A，个人站写 B。我按 <处理方式> 记录，并保留了冲突标注。
